# Two-paragraph breakdown

*Kept short and always up to date — see `.agent/STATUS.md` for full detail, `.agent/ARS.md` for every finding, `.agent/DECISIONS.md` for the reasoning behind real decisions.*

This is a full FreeRTOS rewrite of a coffee-grinder scale's ESP32 firmware (branch `rewrite/rtos-fork`, effectively a permanent fork of `main`): seven tasks (scale sampling, dosing control, input, display, settings, network, telemetry) communicating over queues/mailboxes instead of the old single `loop()`/`switch(state)` machine, a fitted online dosing model (`lib/DosingModel`) replacing a static lookup table, a React/TypeScript SPA served from the device's own LittleFS filesystem at `http://eureka.local/`, and telemetry posted directly to a PostgREST deployment the SPA's History tab also queries straight from the browser. The rewrite has been running on the real physical device (not just build-verified) for a full live-debugging session: a stack of real hardware/firmware bugs were found and fixed this way (buttons wired active-high/active-low asymmetrically but assumed uniform, the load cell's excitation never powered, ADC gain/speed clobbered by init ordering, an OTA display race, a grind-start-baseline bug and a separate mid-grind sensor-glitch bug that both let a session falsely "finish" early, and a settings-exposure gap that made most ADC/timing tunables unreachable from the SPA despite already being validated server-side) — all fixed, with native tests covering the dosing-model-level fixes.

Most recently: an attempt at dynamically switching the ADC's sample rate (fast while the reading is actively changing, precise once settled) was built three different ways, oscillated live each time for the same underlying reason (the ADS1232 driver's own "changing" flag isn't a reliable real-time trigger at any single sample rate), and was reverted at the owner's request rather than keep iterating — logged as a standing finding (AR-050) so a future attempt starts from that premise. The owner then handed off with open-ended direction to review the codebase, keep improving it, and give both the physical display and the SPA a real visual redesign ("should look like an Apple product"). That's in progress: a structural display bug (the boot splash bypassed the main render loop's own mode-change tracking) is fixed, and both surfaces have been reskinned around real iOS/macOS system colors and typography (progress bars and accent details on the TFT within a tight ~85KB flash budget; a full SPA reskin — segmented-control nav, grouped-list settings, status pills — that kept every existing CSS class name so no component logic changed), deployed and confirmed serving on the device. Broader codebase-review work (beyond the display/SPA visual pass) has not started yet.
